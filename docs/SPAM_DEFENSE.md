# Spam & Abuse Defense — one-paragraph summary

Every report is anchored to a phone number (normalized to a canonical digits-only form — `app/services/spam_defense.normalize_phone` — then hashed with a server-side salt before storage, never kept in the clear — `hash_phone`), which is the one identity signal every channel shares. Normalization matters as much as hashing here: without it, the same citizen typing "+254712345678" in one session and "0712345678" in another would silently become two different Reporter identities, each free to submit its own "independent" report on the same project — a real gap this project shipped with and then closed. A phone can hold only one *active* report per project: a second submission edits the first (the old one is marked superseded, never deleted) rather than creating spam, and edits are only accepted inside a rolling window (`REPORT_EDIT_WINDOW_HOURS`, default 24h) so the same person can correct themselves without being able to flood a project with duplicates. A sliding-window burst check (`BURST_MAX_REPORTS` reports within `BURST_WINDOW_MINUTES`, default 5 in 10 minutes) and a cross-ward anomaly check (a number with no report history suddenly reporting across `NEW_NUMBER_MULTI_WARD_THRESHOLD`+ unrelated wards, default 3) catch bot-like behavior — but neither *rejects* a report outright; both mark it `excluded_from_aggregation` so it stays visible in the audit trail (nothing is ever silently deleted) while it's held out of the count that can move a project to `Disputed`, pending review. On top of that, each reporter carries an internal-only reputation score that nudges up when their claim is later corroborated by independent others and down when it isn't (`update_reputation` in `report_service.py`); this score is never exposed on any public API response or UI — it only weights *internal* thresholds, precisely so a first-time or vulnerable reporter with a real story to tell is never publicly branded low-credibility before anyone has had a chance to corroborate them.

**Identity requires OTP verification, for the channels where that's meaningful.** `report_service.submit_report()` rejects (`403 phone_not_verified`) any `channel="app"` or `channel="bluetooth"` report from a phone that hasn't completed `POST /api/auth/verify-otp` — the phone-hash identity above is only a real, hard-to-fake identity once the number has been proven reachable, and a raw REST call previously had no such requirement at all (only the mobile UI's own client-side redirect to the phone-verify screen stood in the way, which anyone calling the API directly could simply skip). WhatsApp and SMS are deliberately exempt: sending a message *from* a number is itself proof of controlling that SIM, so there's no separate OTP step in those flows by design.
