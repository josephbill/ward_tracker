# Spam & Abuse Defense — one-paragraph summary

Every report is anchored to a phone number (hashed with a server-side salt before storage, never kept in the clear — `app/services/spam_defense.hash_phone`), which is the one identity signal every channel shares. A phone can hold only one *active* report per project: a second submission edits the first (the old one is marked superseded, never deleted) rather than creating spam, and edits are only accepted inside a rolling window (`REPORT_EDIT_WINDOW_HOURS`, default 24h) so the same person can correct themselves without being able to flood a project with duplicates. A sliding-window burst check (`BURST_MAX_REPORTS` reports within `BURST_WINDOW_MINUTES`, default 5 in 10 minutes) and a cross-ward anomaly check (a number with no report history suddenly reporting across `NEW_NUMBER_MULTI_WARD_THRESHOLD`+ unrelated wards, default 3) catch bot-like behavior — but neither *rejects* a report outright; both mark it `excluded_from_aggregation` so it stays visible in the audit trail (nothing is ever silently deleted) while it's held out of the count that can move a project to `Disputed`, pending review. On top of that, each reporter carries an internal-only reputation score that nudges up when their claim is later corroborated by independent others and down when it isn't (`update_reputation` in `report_service.py`); this score is never exposed on any public API response or UI — it only weights *internal* thresholds, precisely so a first-time or vulnerable reporter with a real story to tell is never publicly branded low-credibility before anyone has had a chance to corroborate them.
